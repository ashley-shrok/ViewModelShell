<objective>
Land ICON-08: hand-check WCAG AA contrast for every NEW icon-on-tinted-surface fg/bg pair the primitive introduces, across default + all 12 shipped themes, and deepen failing tones per the shipped v3.5.0 pattern.

Purpose: `.vms-icon--{tone}` sets `color:` from an existing tone token, and the SVG's `stroke="currentColor"` inherits that color. When an icon renders ON a tinted surface (icon inside a badge with tone; icon inside a card section with tone), the token pair may or may not pass WCAG AA. The fixed 13-pair `check:aa-contrast` gate covers a curated set of critical pairs but was NOT designed to auto-cover new fg/bg pairs — every new pair introduced by this phase is a manual audit.

Output:
- Audit artifact `22-08-AA-AUDIT.md` documenting per-theme, per-pair ratios + PASS/FAIL.
- Deepening changes (if any) to tone tokens in `default.css` and/or `themes/*.css` — modifying ONLY the failing tone's token, via `color-mix` per the v3.5.0 pattern.
- `check:aa-contrast` still passes; the fixed 13-pair coverage is not regressed.

**Design of record:** `.planning/design/icons-primitive.md` §8. AGENTS.md §"Working agreement" governs the audit discipline. CONTEXT.md `<decisions>` cross-references the banked lesson about the auto-gate's blind spot.

**This plan is `autonomous: false`** — it requires a human hand-check because the fixed `check:aa-contrast` gate doesn't automate new-pair coverage. An agent CAN compute the contrast ratios (there are token color values in CSS, WCAG has a deterministic algorithm), but the "does this rendered pair look right at all 12 themes" review needs Ashley's eye. The plan produces the audit artifact + any mechanical deepening; sign-off is human.

**Dependencies:** Plan 04 (browser renderer + `.vms-icon*` CSS) must have landed. The audit works from the shipped classes; it doesn't audit anything until the classes exist.
</objective>

2. Compute WCAG 2.1 contrast ratio via the standard algorithm ((L1 + 0.05) / (L2 + 0.05) where L is relative luminance).
3. Threshold:
   - **3.0:1** for graphical-state-indicator icons (WCAG 1.4.11 non-text UI-component contrast) — acceptable ONLY when state is also carried by non-color channels (per must_haves.truths). For icons in this phase, aria-label + shape ARE always the primary channels (Plan 01's a11y contract), so 3.0:1 suffices for meaning-carrying icons.
   - **4.5:1** for AA on text-like adjacent icons (icon-in-button where the icon augments text semantics).
   - **Icons that are purely decorative** (`label` absent → `aria-hidden`) don't need to meet contrast at all — screen readers ignore them; sighted users see them as embellishment. Still: aim for ≥3.0:1 for basic legibility.
4. Populate the audit table in `22-08-AA-AUDIT.md`: one row per (theme, pair, ratio, PASS/FAIL against 3.0 threshold).

<risk_summary>
- **The 13-pair gate's blind spot is the whole reason for this plan.** Do NOT assume `check:aa-contrast` passing means the phase's new pairs pass. The audit is manual by design (banked lesson); the gate is not a substitute.
- **Modify the TOKEN, not the icon class.** If icon-on-danger fails, don't add `.vms-icon--danger { color: <deeper-color>; }` as an override — that would branch icon colors from text colors, breaking the "SVG stroke inherits currentColor" simplicity. Deepen `--vms-danger-fg`; every use of the token (icons, text, badges, buttons) improves together.
- **`autonomous: false` means the executor produces the audit artifact + mechanical deepenings, then STOPS.** Ashley reviews before this plan is marked complete. Do NOT proceed to Plan 09 (demo + verification page) until Ashley signs off.
- **Colorblindness is out of scope for this plan.** Icons are inherently colorblind-safe (shape + aria-label channels — CONTEXT.md decisions §"A11y + colorblindness"). Contrast is the concern here; palette safety is Plan 01's a11y contract.
</risk_summary>
