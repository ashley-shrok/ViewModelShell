<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Lazy import loader → TipTap bundle | If a network/CDN issue or a build misconfiguration prevents TipTap from loading, the app has no rich text capability. The fail-loud rule (AGENTS.md §The capability seam) mandates a hard `console.error` — never a silent no-op that would swallow user input. |
| turndown HTML → markdown conversion | Malicious HTML pasted into the editor could produce malicious markdown that, when re-rendered via `marked` → InlineRuns, could carry XSS payloads. Plan 28-06 audits the READ side (`markdown.ts`); this plan's turndown output feeds that pipeline. |
| Editor instance persistence | The reused-editor mechanism (across renders) trusts that `editorInstances.get(key).editor` was created by THIS process and has not been tampered with. Standard trust for in-process state; no cross-origin surface. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-07 | Denial of Service | TipTap load failure | mitigate | fail-loud via `richTextFailLoud()` → `console.error` (Task 2). Never silent no-op. Consumer environments with network restrictions see a hard failure they can debug, not a mysteriously-broken input. Plan 28-06's threat model considers whether to ship a `RichTextFieldNode` behavior for the failure case beyond fail-loud (currently: no fallback textarea; consumer must resolve). |
| T-28-08 | Tampering | Bundle bloat (D-04 violation) | mitigate | Task 4 test #1 (`does NOT resolve @tiptap/core if no RichTextFieldNode renders`) is the CI-blocking assertion. A future refactor moving the import to top-level fails this test loudly. This is the exact class of guarantee gotcha #9 exists to protect — the invariant needs a test that can PROVE it, not just a code review that hopes for it. |
| T-28-09 | Elevation of Privilege | Editor XSS via malicious markdown output | transfer | Plan 28-06 owns the READ-side sanitization audit. This plan's turndown output is normal markdown; if a paste-time HTML sanitization gap surfaces (e.g. TipTap's StarterKit accepts `<script>` in a paste event), Plan 28-06 or a follow-up bounty closes it. The wire itself (markdown string) has zero XSS surface per D-06. |
| T-28-10 | Information Disclosure | Editor content in browser bundle | accept | The user's typed markdown lives in the browser's DOM + the shell's in-memory state until the next dispatch, at which point it round-trips via `_state`. No new disclosure surface vs. any FieldNode(textarea). |
