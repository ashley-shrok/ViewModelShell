<objective>
Execute the Q4 sanitization audit deferred from 28-CONTEXT.md § Claude's Discretion. The rich text primitive's wire is a markdown string (per D-06, zero XSS on the wire ITSELF). The READ-side risk surface is the existing markdown display pipeline: if a user types `[link](javascript:...)`, does the shipped `markdown.ts` + Markdown companion NuGet emit that scheme unfiltered into the rendered `InlineRun.href`? This plan audits both backends, adds a shipped scheme-whitelist sanitizer if a gap exists, tests the surface adversarially, and produces a durable AGENTS.md note so the audit result cannot silently regress.

Purpose: Rich text is the first primitive where user-authored markdown will commonly round-trip back into the rendered view (a note, a comment, a message body). Every prior consumer of the markdown pipeline was rendering DEVELOPER-authored markdown (from `.md` files, README content, etc.), so a `javascript:` scheme in a link was a theoretical concern. With Phase 28, it becomes a real one. Closing the audit now is cheaper than fixing an actual XSS report against a shipped rich text field.

Output: A recorded audit result + (if needed) a shipped whitelist sanitizer + tests + a documented contract.
</objective>

    ```typescript
    /** Shipped whitelist of allowed URL schemes for markdown-emitted hrefs.
     *  Runs BEFORE the opt-in `linkHrefRewrite` hook (so a consumer's hook
     *  sees an already-sanitized href — or an empty string for disallowed
     *  schemes). Whitelist chosen over blocklist per web-security orthodoxy:
     *  unknown schemes default to safe, not exploitable.
     *
     *  Allowed: http, https, mailto, tel, ftp; relative URLs without scheme.
     *  Disallowed (returns ""): javascript:, data:, vbscript:, file:, and
     *  ANY other scheme not in the whitelist. */
    const ALLOWED_LINK_SCHEMES = ["http", "https", "mailto", "tel", "ftp"];
    function sanitizeHref(raw: string): string {
      const trimmed = raw.trim();
      // Relative or fragment / query → allowed (no scheme).
      const schemeMatch = /^([a-zA-Z][a-zA-Z0-9+.\-]*):/.exec(trimmed);
      if (!schemeMatch) return trimmed;
      const scheme = schemeMatch[1].toLowerCase();
      return ALLOWED_LINK_SCHEMES.includes(scheme) ? trimmed : "";
    }
    ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User-authored markdown → InlineRun.href → rendered `<a>` | The exact XSS surface for content-round-tripped rich text. Prior to Phase 28 this was a theoretical concern (only developer-authored markdown flowed here); now it's real. |
| `linkHrefRewrite` hook (opt-in) | Consumers who override may inadvertently pass-through disallowed schemes — this plan makes the shipped default safe REGARDLESS of consumer config. |
| Autolinks vs regular links | Two markdown syntaxes emit the same InlineRun.href but through different converter paths. Task 1's audit must cover BOTH; a fix that misses autolinks leaves the gap open. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-16 (Phase T2) | Elevation of Privilege | markdown → InlineRun.href renders `javascript:` | mitigate | Task 2 adds shipped whitelist sanitizer if the audit surfaces the gap. Whitelist over blocklist — unknown schemes default to safe. Runs BEFORE the consumer's opt-in `linkHrefRewrite` so consumer config cannot re-introduce the gap accidentally. |
| T-28-17 (Phase T3) | Elevation of Privilege | TipTap StarterKit allowing raw HTML input | accept | TipTap StarterKit's default set does NOT include the `HTML` extension; there's no way to enter arbitrary `<script>` via the toolbar UI. Paste sanitization (TipTap default) strips unknown HTML tags. If a consumer explicitly opts into raw HTML by extending TipTap themselves, that's outside the framework's contract. |
| T-28-18 | Denial of Service | Sanitizer regex catastrophic backtracking | mitigate | The scheme regex `/^([a-zA-Z][a-zA-Z0-9+.\-]*):/` is bounded, non-backtracking. Task 3 tests verify runtime — but a follow-up bounty could add a fuzzer if this becomes a real concern. |
</threat_model>
